# Shortcut System

A shortcut is a pipeline from "the user pressed a key" to "some code runs". [src/renderer/services/shortcuts/](../src/renderer/services/shortcuts/) holds every part; [components/shortcut-host.tsx](../src/renderer/components/shortcut-host.tsx) is the wire connecting them. It serves two entrances at once: keyboard events, and native menu clicks.

The contract lives in [shared/shortcuts.ts](../src/shared/shortcuts.ts) and [shared/command-catalog.ts](../src/shared/command-catalog.ts), shared by both ends — the main process reads the same catalog to generate menu accelerators (see [Application Menu](./main-menu.md)).

## Catalog and validation

`commandCatalog` is the **single command list**: command ids to `CommandDefinition` (title, description, scope, defaultBindings, allowInEditable, allowRepeat). Currently about 30 commands, all under the `workbench` scope: sidebar toggle, new session, close session, back/forward, tab cycling, nine tab slots, nine sidebar slots, and a row of pickers (model, permission, project, session, all sessions, sent messages, quick switch).

`workbench.tab.activate.1..9` and `workbench.sidebar.session.activate.1..9` are batch-generated by `Object.fromEntries`, not hand-written 18 times.

[validateCommandCatalog](../src/renderer/services/shortcuts/catalog.ts) runs once at runtime construction; **errors in the catalog itself throw immediately**, never waiting for runtime:

- Every command must declare at least one scope
- `ANY_SHORTCUT_SCOPE` (`'*'`) cannot combine with other scopes — mixing "hits anywhere" with "scoped" would gut the depth arbitration below
- Default bindings must pass `getShortcutBindingIssue`, and one command cannot hold duplicate signatures
- Default bindings must have no **hard** conflicts: it calls `findShortcutConflicts` back, checking every pair of default bindings with empty overrides

Meaning: **conflict detection serves not only user rebinding — it is also the catalog's self-check**.

## Binding semantics

[bindings.ts](../src/renderer/services/shortcuts/bindings.ts) defines how bindings normalize, compare, and display.

**Normalization**: `normalizeShortcutBinding` orders modifiers by the fixed `MODIFIER_ORDER` (primary → ctrl → alt → shift → meta), deduping and sorting, with key names through `KEY_ALIASES` (`' '` → `space`, `esc` → `escape`, `return` → `enter`). Bindings written in different orders therefore normalize identically.

**`primary` is platform-dependent**: `resolveModifier` resolves `primary` to `meta` on mac and `ctrl` elsewhere. A catalog entry `{ modifiers: ['primary'], key: 'b' }` is thus ⌘B on mac and Ctrl+B on Windows/Linux, written once.

**Signature**: `bindingSignature`'s string **drops primary**, using only the remaining modifiers plus the key name (`MODIFIER_ORDER` minus primary, joined, then `|` and the key). Deliberate: the signature judges "are these two bindings the same key on the same platform", and primary should collapse to the same physical key per platform.

**Event matching**: `eventMatchesShortcutBinding` reads ctrl/alt/shift/meta live from the `KeyboardEvent`, gets the key name via `shortcutEventKey`, then compares signatures. `shortcutEventKey` has a mac special case: **with Option held, `event.key` becomes the typed character** (⌥[ yields `“`), so it reverse-looks-up `event.code` — `KeyB`-style codes take the letter directly, and `MAC_OPTION_CODE_KEYS` covers digit and symbol keys (shift selecting the second entry). Without Option it uses `event.key` directly.

**Display**: `shortcutBindingKeyLabels` picks the modifier order per platform (mac ⌃⌥⇧⌘, others Ctrl+Alt+Shift+Meta), keys through `KEY_LABELS` (arrows become ←↑→↓, enter becomes Enter, unregistered keys uppercase). `formatShortcutBinding` on mac **concatenates with no separator** (`⌘⇧K`), other platforms join with `+`.

## Registry

[registry.ts](../src/renderer/services/shortcuts/registry.ts)'s `createCommandRegistry` is a `Map<CommandId, {enabled, handler, token}>` answering "is anyone executing this command right now".

- `register` requires the command exist in the catalog, and **each command registers at most once** (duplicate registration throws, preventing two components from grabbing one command)
- Returns `{dispose, setEnabled}`; `dispose` deletes only after token validation, `setEnabled` skips unchanged values
- Every register/unregister/enabled change calls `emit()`, incrementing version and notifying listeners — `getVersion()` serves external cache invalidation

A command's "availability" has two layers: **registered or not** (does a component own it) and **enabled** (can that component act right now). `workbench.session.close` is exactly enabled-false when no session is selected.

## Keymap merging

[keymap.ts](../src/renderer/services/shortcuts/keymap.ts)'s `getEffectiveBindings` is one sentence: **when overrides has the command's own property (`Object.hasOwn`), use overrides; otherwise defaultBindings**, uniformly normalized after.

It uses `hasOwn` rather than truthiness, so **an empty array is a legal override** — meaning "I cleared this command", not "use the default".

## Scopes

### scopeMatches

```
if (commandScope === ANY_SHORTCUT_SCOPE) return true
return currentScope === commandScope || currentScope?.startsWith(`${commandScope + '.'}`) === true
```

A command's declared scope is a **prefix**: `workbench` matches `workbench` and `workbench.sidebar`, while `settings` matches only `settings` itself. With no active scope (`null`), only `*` matches.

### The scope manager

[scope.ts](../src/renderer/services/shortcuts/scope.ts)'s `createShortcutScopeManager` maintains a **frame stack**: `activate(scope, owner)` pushes a frame and returns the pop function. The difficulty is "the stack top is not necessarily the current scope" — `getCurrent()` starts at the top, and when that frame carries an owner, it searches the whole stack for frames **whose owner descends from it**, descending to the deepest one.

This solves React's unmount order not matching scope nesting order: a child owner under one parent may pop later than the parent. Descent is judged by token chains, not array position.

`emitIfChanged` notifies listeners only when **the resolved result truly changed**.

### ANY_SHORTCUT_SCOPE

`'*'` means "this command responds everywhere". Two special treatments:

- **`validateCommandCatalog` forbids combining it with other scopes** (above)
- **It poisons arbitration**: in `resolveActiveBindings`, if any candidate group sharing a key signature has `*` as its matching scope, **the whole group drops** — `*` has no depth, making fair arbitration with it impossible. Better that the key dies entirely than guessing a winner

So `*` effectively suits commands **exclusively** owning a key.

### The capture manager

`createShortcutCaptureManager` is an independent little machine: a token set where `begin()` adds and returns a release function, and `getSnapshot()` is `owners.size > 0`. It is true while recording a shortcut, **freezing global key handling entirely** (below), and notifying the main process to strip menu accelerators.

## Arbitration

[resolver.ts](../src/renderer/services/shortcuts/resolver.ts) is the system's densest module, with two exports serving two moments: resolving the active bindings when a key lands (`resolveActiveBindings`), and checking conflicts when the user finishes recording (`findShortcutConflicts`).

### scopeDepth and deepestMatchingScope

`scopeDepth` numbers scopes: `*` is **-1**, others are dot-segment counts (`workbench` = 1, `workbench.sidebar` = 2). `deepestMatchingScope` picks, from all scopes a command declares, the **deepest one matching the current scope** — a command may declare several scopes and is judged at its current deepest.

### scopeConflictType

Two scopes colliding are classified:

- Either is `*`, or they are equal → **hard**
- One is the other's prefix (`workbench` vs `workbench.sidebar`) → **shadow**
- Otherwise → no conflict

**hard** means "these scopes may be active simultaneously; the key genuinely races"; **shadow** means "the specific one always covers the broad one — the covered binding dies but is not a design error".

### resolveActiveBindings

After a key lands, `ShortcutHost` calls it for "the bindings actually in effect now":

1. `isCapturing` true → return `[]` directly
2. Walk the catalog, skipping commands **unregistered** or **disabled**, computing each command's match depth via `deepestMatchingScope`; no match, skip
3. Each command's effective bindings compute signatures and group by signature; a command appears once per signature group (multiple bindings hitting one signature take the first)
4. **In-group arbitration**: more than one candidate and any `*` → the whole group drops; otherwise take the max depth, and **the deepest candidate must be exactly one**, else the whole group drops

The last two rules are one philosophy applied twice: **when a winner cannot be uniquely determined, the key does nothing**. Conflicts never silently race; they disable outright — the user sees "nothing happened", goes to settings, and rebinds, instead of mysteriously triggering some other command.

### findShortcutConflicts

Given a candidate binding, scan the whole catalog for other commands with the **same signature**, pairwise computing `scopeConflictType` over both sides' scopes, with hard overriding shadow (any hard pair classifies hard). The recorder consumes it: hard blocks saving, shadow allows saving with an "it will be masked" notice.

## Override storage

[overrides.ts](../src/renderer/services/shortcuts/overrides.ts)'s `createShortcutOverridesStore(client)` is the renderer-side cache, never persisting itself — load/set/reset all delegate to a `ShortcutOverridesClient`.

The snapshot trio: `{error, isLoaded, overrides}`. `initialize()` **succeeds once** (`isLoaded && !error` resolves directly; an in-flight promise is reused), and on failure records the error in the snapshot but still sets `isLoaded` true — so "load failed" and "still loading" stay distinguishable, letting callers handle each. `mutate` awaits initialize first, then emits a new snapshot on success and returns a **deep copy**, merging the error into the current snapshot and rethrowing on failure.

`cloneOverrides` copies every binding along with its modifiers array, preventing external mutation of internal state.

The write side [desktop.ts](../src/renderer/services/shortcuts/desktop.ts): `load` returns `{}` off the desktop runtime, while `set` / `reset` **require the desktop runtime** (otherwise throwing `Shortcut settings are only available in the desktop app`). The three RPCs are `shortcutGetOverrides` / `shortcutSetOverride` / `shortcutResetOverride`.

The main-process side [shortcuts.ts](../src/main/shortcuts.ts) is where persistence actually happens: `createShortcutStore` serializes writes into a **tail chain** (each update chains after the last, so concurrent sets never overwrite each other), persisting before updating memory. Disk writes use **temp file plus rename** (`.shortcuts.json.<pid>.<uuid>`, `mode: 0o600`), never in-place overwrites. `set` validates each binding, throwing on illegal before entering the chain.

## How an override reaches two places

This is the system's only "change once, take effect twice":

- **Menu accelerators**: [bootstrap.ts](../src/main/bootstrap.ts)'s `resolveCommandBindings` checks the shortcutStore — non-empty overrides win, otherwise `commandCatalog[commandId].defaultBindings`. The `shortcutSetOverride` / `shortcutResetOverride` handlers **rebuild the application menu immediately** after changing storage, so menu shortcut labels update in sync.
- **The renderer's key table**: when `runtime.overrides`'s snapshot changes, `ShortcutHost`'s `useHotkeys` callback picks up the new values next time.

`ApplicationMenuOptions.commandBindings` is that seam: [application-menu.ts](../src/main/application-menu.ts)'s `commandMenuItem` takes `bindings[0]` into an accelerator (`bindingToAccelerator` maps `primary` to `CmdOrCtrl`, keys through `ACCELERATOR_KEYS`), and when `isCaptureActive` is true **no accelerator is attached at all** — otherwise the menu would swallow recorded keystrokes.

## Dispatch

[dispatcher.ts](../src/renderer/services/shortcuts/dispatcher.ts)'s `dispatchCommand` is the terminus, returning `'unavailable' | 'handled' | 'failed'`: unregistered or disabled returns unavailable; a handler throw logs `shortcut.failed` and returns failed — **one shortcut failing never becomes an unhandled rejection**.

## Assembly

[runtime.tsx](../src/renderer/services/shortcuts/runtime.tsx)'s `createShortcutRuntime` builds all five parts in one pass: `capture`, `overrides`, `registry`, `scopes`, plus `catalog` and `platform`.

The client is wrapped in a **`whitelistClient`**: `load` filters every read binding through `isShortcutBinding`, `set` runs `assertKnownCommand` (must be in the catalog) then validates each binding, `reset` passes through. Storage-side validation thus has two layers.

`detectShortcutPlatform` guesses the platform from the UA (`mac` / `win` → windows / else linux), **defaulting to linux without a navigator** — giving tests a deterministic value.

The module-level singleton `shortcutRuntime` builds one instance from `commandCatalog` plus `desktopShortcutOverridesClient`, delivered through `ShortcutRuntimeProvider`; `useShortcutRuntime()` throws `ShortcutRuntimeProvider is missing` when absent.

## The event entrance

[shortcut-host.tsx](../src/renderer/components/shortcut-host.tsx) returns null — a pure logic component, three effects plus one `useHotkeys`:

1. **Initialize overrides**: `runtime.overrides.initialize()`
2. **Menu commands**: subscribe to the `menu-command-dispatch` push, calling `dispatchCommand` directly. Menu clicks therefore share the keyboard's terminus, behaving identically by construction
3. **Capture-state sync**: `runtime.capture.subscribe` calls `applicationMenuSetCaptureActive`, telling the main process the renderer's recording state
4. **Global keys**: `useHotkeys('*')` with `enableOnFormTags` / `enableOnContentEditable` / `preventDefault: false` — **every key arrives here first, and this decides whether to pass it through**

The `useHotkeys` callback's order matters: first check `event.isComposing` (never intercept IME composition), then whether overrides `isLoaded` (never intercept before load, or defaults would clobber user overrides), then `resolveActiveBindings` finds the winner matching the pressed key, and only then the definition decides:

- `event.repeat && !allowRepeat` → skip (long-press does not repeat; every command in the catalog is `allowRepeat: false`)
- `isEditableTarget(event.target) && !allowInEditable` → skip. `isEditableTarget` checks `input, textarea, select`, `isContentEditable`, and the nearest `[contenteditable="true"]` ancestor. Every command in the catalog is `allowInEditable: true`, so this currently always passes — reserved for future commands
- Only then `preventDefault()` and dispatch

`preventDefault` coming last is intentional: keys not being handled must **reach the page untouched**, or inputs would stop receiving characters.

## Component-side hookup

### useCommandHandler

[use-command-handler.ts](../src/renderer/hooks/use-command-handler.ts) is the sole entrance for a component declaring "I own this command":

```ts
useCommandHandler('workbench.session.close', () => { … }, { enabled: Boolean(selectedSession) })
```

It uses three refs to split **registration** from **updating**: `handlerRef` / `enabledRef` refresh inside a layout effect, while the registering effect depends only on `[commandId, registry]` — so a handler that is a new function every render never re-registers; enabled changes flow through another effect calling `registration.setEnabled`.

`enabled` is expressed through that option, with no separate `useCommandEnabled` hook: the registration handle's `setEnabled` is the same capability, and the hook merely wraps it as a declarative parameter. Unregistration happens in the effect cleanup's `dispose()`.

### ShortcutScope

[shortcut-scope.tsx](../src/renderer/components/shortcut-scope.tsx) wraps scopes as components: `ShortcutScope` takes the parent owner from context, `createOwner(parent)` builds its own, activates `activate(scope, owner)` in a layout effect, and provides the new owner context. `scope={null}` means inactive (for UI mounted conditionally by toggles).

### ShortcutDialog

[shortcut-dialog.tsx](../src/renderer/components/shortcut-dialog.tsx) wraps Dialog and AlertDialog once each: **opening switches the scope to `overlay`**, closing switches back to null. Any popped dialog therefore automatically claims the shortcuts — ⌘B in the session page cannot trigger something in the settings page.

Both `defaultOpen` / `open` controlled and uncontrolled modes are supported, with `onOpenChange` forwarded untouched.

## The recorder

[recorder.ts](../src/renderer/services/shortcuts/recorder.ts)'s `interpretShortcutCapture(event, platform)` translates a native key event into one of five results:

| Result | Trigger |
| --- | --- |
| `wait` | `event.isComposing`, or a modifier key still held |
| `cancel` | Escape |
| `clear` | Backspace / Delete with no modifiers |
| `invalid` | legal shape but `bare-printable` (an unmodified single character) |
| `binding` | everything else |

Modifier collection differs from display: here `metaKey` on mac records `primary` and elsewhere `meta`, with `ctrlKey` the reverse — matching `eventModifiers`' comment, both mapping physical keys to logical modifiers per platform.

[shortcut-recorder.tsx](../src/renderer/pages/settings/components/shortcut-recorder.tsx) is the recording dialog (the settings table is in [Settings Page](./renderer-settings.md)): opening calls `runtime.capture.begin()` to claim the keyboard (`endCapture` runs in cleanup, released on unmount too), then `interpretShortcutCapture` dispatches — `cancel` closes, `clear` empties the binding, `invalid` reports `requiresModifier`, and a binding immediately runs `findShortcutConflicts`.

Saving goes through `runtime.overrides.set(commandId, binding ? [binding] : [])` — **an empty array means clear**, aligned with `getEffectiveBindings`'s `hasOwn` semantics. Hard conflicts disable the save button; shadow conflicts only warn "will override some command" and permit saving.
